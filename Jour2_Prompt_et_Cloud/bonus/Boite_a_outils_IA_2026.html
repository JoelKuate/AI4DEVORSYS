Section 01 · principe

Harnais et agents de code : de quoi parle-t-on ?

Un harnais d'agent donne au modèle un terminal, des fichiers, des permissions et une boucle de correction. Deux harnais avec le même modèle donnent des résultats très différents.

Ce qu'il faut garder de la section 01

  • Choisir un harnais, c'est choisir : qui valide chaque action, où tourne le code et quels modèles on peut brancher.

À retenir · Moteurs d'inférence et runtimes

Ce qu'il faut garder de la section 05

  • Même GGUF, même moteur : sur NVIDIA, l'écart entre llama.cpp, Ollama et LM Studio reste faible (quelques pour cent). Le choix est un choix de confort.
  • Sur Mac, un backend MLX peut dépasser nettement llama.cpp. Sur serveur multi-utilisateurs, vLLM ou SGLang multiplient le débit.
  • Toutes ces options exposent une API compatible OpenAI : votre code client ne change pas, seule l'URL de base change.

Synthèse · quantification

Lire les suffixes : Q8_0, Q6_K, Q5_K_M, Q4_K_M, IQ4_XS…

VarianteBits / poids (ordre de grandeur)QualitéQuand l'utiliser
F16 / BF1616référenceConversion, fine-tuning, serveur GPU
Q8_0~8,5quasi identiquePoste puissant, si la mémoire le permet
Q6_K~6,6excellenteBon compromis haut de gamme
Q5_K_M~5,7très bonneRemplace Q8 quand la mémoire manque
Q4_K_M~4,9bonneDéfaut raisonnable pour la plupart des cas
IQ4_XS~4,3bonneUn peu plus petit que Q4_K_M, un peu plus lent

Règle d'or : un modèle plus petit en Q5/Q6 bat très souvent un modèle plus grand en Q2. Les valeurs de bits sont approximatives et varient selon l'architecture.
Synthèse · dimensionner

Combien de mémoire pour quel modèle ?

  • Formule de départ : taille du fichier ≈ paramètres (en milliards) × bits ÷ 8. Exemple : 8 × 4,9 ÷ 8 ≈ 4,9 Go.
  • Ajoutez le cache de contexte (KV cache) : de 1 à plusieurs Go selon la longueur, qui peut être le facteur limitant sur de longs contextes.
  • Prévoyez 20 à 30 % de marge pour le système et les autres applications.

🔧 Travaux pratiques

Construire sa propre boîte à outils en une heure

60 minutes · en binôme
  1. Choisissez un cas d'usage réel de votre équipe (assistant documentaire, revue de code, extraction de factures…).
  2. Pour chaque catégorie du plan, retenez un seul outil et écrivez en une phrase pourquoi vous l'écartez les autres.
  3. Lancez un modèle local avec Ollama ou LM Studio et appelez-le depuis un script avec l'URL de base compatible OpenAI.
  4. Ouvrez les deux dépôts les plus importants de votre sélection : relevez la licence, le dernier commit et le nombre de tickets ouverts.
  5. Relevez dans la fiche d'un modèle GGUF : licence, langue, taille, quantification choisie et la mémoire que votre machine devra fournir.
  6. Rédigez les trois risques de votre pile (confidentialité, dépendance, maintenance) et une mesure pour chacun.
Livrable : une page « pile technique » avec un outil par catégorie, une justification d'une phrase, et les trois risques avec leur parade.

Bilan

Les cinq idées à garder

  • Le harnais compte autant que le modèle : choisissez qui valide, où ça tourne, quels modèles se branchent.
  • Le format suit le moteur : GGUF pour le local, safetensors/AWQ pour les serveurs, MLX pour Apple.
  • Q4_K_M ou Q5_K_M pour commencer ; un modèle plus petit bien quantifié bat un gros modèle écrasé.
  • Prompt, puis RAG, puis fine-tuning : dans cet ordre, parce que le coût est multiplié par dix à chaque étape.
  • Ce qui n'est pas mesuré n'est pas amélioré : évaluez, tracez, anonymisez.
